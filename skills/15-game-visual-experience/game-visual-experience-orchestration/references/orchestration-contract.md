# Game Visual-Experience Orchestration Contract

Return to [the parent skill](../SKILL.md).

## Ownership

| Concern | Owner | Boundary |
|---|---|---|
| Player promise, gameplay systems and production implementation | software game-development engine | This design route consumes the approved intent and build constraints |
| Game visual and interaction craft | this group and existing design specialists | It does not prescribe engine code or SRS phase structure |
| Lifecycle requirements and traceability | SRS engine | It records requirements and evidence links, not craft doctrine |
| Source verification and claim provenance | digital-research engine | Research is not cultural permission or player evidence |

## Loop-to-presentation row

Record: player question; verb; input; world cue; HUD cue; feedback channels; camera; failure/recovery; stopping state; access/localisation alternatives; platform and budget; business surface; evidence class; owner; unresolved decision.

## Evidence classes

Use `documented`, `prototype-observed`, `build-executed`, `device-measured`, `player-observed`, or `accountable-expert-approved`. A stronger class never follows automatically from a weaker one. Learning and cultural acceptance need their own named evidence.

## Gate order

Player promise → representative loop → access/safety/culture → craft specialists → handoff → build identity → device checks → player or expert evidence → release decision. A failed upstream gate blocks stronger downstream claims.

## Non-intrusive commercial surfaces

Ads and offers must be clearly identified, voluntary where rewarded, and limited to a predictable genuine break after the requested action completes. They cannot appear during play, learning, narrative, saving, recovery, pause-to-stop, or exit. Specify decline/close, cap/pace, no-fill/offline/SDK-failure, audience treatment, data/consent, and kill switch. Unknown child or privacy treatment fails closed.
